     1→# Design System PRD — Vanilla JavaScript UI Component Platform
     2→
     3→Version 1.0 · Brand identity, visual language, UI foundations, iconography, and interaction standards
     4→
     5→The design direction should feel like a professional software workshop with a distinctive, slightly experimental identity: nearly black surfaces, deep purple structure, and a sharp light-lemon-green accent.
     6→
     7→It should communicate precision, flexibility, and technical independence—not look like a generic SaaS dashboard or a conventional UI component gallery.
     8→
     9→The same design system must serve two different purposes:
    10→
    11→- The platform website: a polished developer workspace for discovering, testing, and understanding components.
    12→- The component library: reusable, framework-independent vanilla JavaScript components whose visual styling can be customized independently of the documentation website.

    54→### The visual signature
    55→
    56→The brand should be recognizable through the combination of:
    57→
    58→1. Near-black backgrounds and dark-purple structural surfaces.
    59→2. Light lemon green for active states, primary actions, and key indicators.
    60→3. Fine borders and carefully layered surfaces instead of excessive shadows.
    61→4. Compact developer-tool layouts with generous spacing around important content.
    62→5. Geometric iconography and restrained abstract branching or connected-node motifs.
    63→
    64→Design rule: Purple establishes the environment; lemon green identifies the action. Green should not cover every surface or turn the interface into a neon theme.

   172→## 3. Typography
   173→
   174→Typography should combine a contemporary sans-serif for interface clarity with a compact monospace face for code, values, and technical metadata.
   175→
   176→### Recommended font stack
   177→
   178→HEADINGS & INTERFACE
   179→
   180→# Inter
   181→
   182→Use Inter or a comparable neutral sans-serif for navigation, headings, buttons, labels, and body text.
   183→
   184→CODE & TECHNICAL VALUES
   185→
   186→# JetBrains Mono
   187→
   188→Use for code snippets, keyboard shortcuts, numeric property values, CSS tokens, and API signatures.
   189→
   190→Both fonts are available through open font projects. Prefer self-hosting licensed font files where practical, with system-font fallbacks.
   191→
   192→### Type scale
   193→
   194→| Token     | Size / line height | Usage                                |
   195→| --------- | ------------------ | ------------------------------------ |
   196→| `display` | 44 / 52 px         | Homepage hero only                   |
   197→| `h1`      | 32 / 40 px         | Main page title                      |
   198→| `h2`      | 24 / 32 px         | Major section heading                |
   199→| `h3`      | 20 / 28 px         | Subsection heading                   |
   200→| `h4`      | 16 / 24 px         | Card and panel headings              |
   201→| `body-lg` | 16 / 26 px         | Introductions and lead text          |
   202→| `body`    | 14 / 22 px         | Standard interface and documentation |
   203→| `body-sm` | 13 / 20 px         | Secondary information                |
   204→| `caption` | 12 / 16 px         | Metadata and helper text             |
   205→| `code`    | 13 / 20 px         | Code and technical values            |
   206→
   207→Use font weights 400 for body text, 500 for interface labels, 600 for section headings, and 700 sparingly for strong emphasis.
   208→
   209→Typography rules
   210→
   211→- Use sentence case rather than all caps for most labels.
   212→- Reserve uppercase text for small technical overlines or status metadata.
   213→- Avoid overly tight line-height in documentation.
   214→- Keep paragraphs at a comfortable reading width.
   215→- Use tabular numerals for changing numeric values where supported.
   216→- Do not make every heading bold or every label monospace.

   218→## 4. Spacing and layout
   219→
   220→Use a consistent four-pixel base grid.
   221→
   222→| Token      | Value | Typical use                    |
   223→| ---------- | ----- | ------------------------------ |
   224→| `space-1`  | 4 px  | Icon-to-label gaps             |
   225→| `space-2`  | 8 px  | Compact control spacing        |
   226→| `space-3`  | 12 px | Input and list spacing         |
   227→| `space-4`  | 16 px | Standard component padding     |
   228→| `space-5`  | 20 px | Card content spacing           |
   229→| `space-6`  | 24 px | Section spacing                |
   230→| `space-8`  | 32 px | Large group separation         |
   231→| `space-10` | 40 px | Page section separation        |
   232→| `space-12` | 48 px | Major layout transitions       |
   233→| `space-16` | 64 px | Hero and major section spacing |
   234→
   235→### Layout dimensions
   236→
   237→- Global header: approximately 60–68 px high.
   238→- Desktop documentation sidebar: approximately 224–256 px wide.
   239→- Contextual right sidebar: approximately 180–220 px wide.
   240→- Main content maximum width: approximately 1,200 px, with wider workspace layouts permitted.
   241→- Standard input height: 36–40 px.
   242→- Compact toolbar control height: 28–32 px.
   243→- Standard button height: 36–40 px.
   244→- Touch-target size: aim for at least 44 × 44 px on touch interfaces.
   245→
   246→The playground may use a wider, application-like layout than standard documentation pages. Do not force every page into the same narrow content column.

   249→
   250→The interface should feel precise but not sterile. Use moderately rounded corners, crisp dividers, and limited depth rather than excessive pill shapes and floating cards.
   251→

   253→

   255→
   256→Standard
   257→
   258→Inputs, buttons, cards, panels
   259→
   260→Soft
   261→
   262→Large previews, dialogs, feature areas
   263→
   264→Pill
   265→
   266→Chips, tags, segmented controls where suitable
   267→
   268→### Border radius tokens
   269→
   270→- `radius-sm`: 4 px.
   271→- `radius-md`: 8 px.
   272→- `radius-lg`: 12 px.
   273→- `radius-xl`: 16 px.
   274→- `radius-pill`: 999 px.
   275→
   276→### Border and shadow rules
   277→
   278→- Use subtle neutral borders to separate adjacent surfaces.
   279→- Reserve stronger purple borders for selected or emphasized regions.
   280→- Use a visible accent-colored focus ring for keyboard focus.
   281→- Prefer one subtle elevation level for overlays and popovers.
   282→- Avoid shadows on every card and button.
   283→- Use glow effects only for exceptional emphasis, never as a default state.

   388→## 8. Component visual language
   389→
   390→The platform should distinguish between brand UI and demonstrated component UI.
   391→
   392→Brand UI includes navigation, documentation panels, the playground shell, buttons, and property inspectors. These use the black, purple, and lemon palette.
   393→
   394→Demonstrated components should use their own neutral or configurable styling so developers can judge their appearance independently of the platform branding.
   395→
   396→### 8.1 Buttons
   397→
   398→Primary action
   399→
   400→Primary
   401→
   402→Lemon background, near-black text. Use for one dominant action per region.
   403→
   404→Secondary action
   405→
   406→Secondary
   407→
   408→Purple surface with readable text. Use for alternative actions.
   409→
   410→Outline action
   411→
   412→Outline
   413→
   414→Transparent or neutral surface with a visible border.
   415→
   416→Text action ↗
   417→
   418→Text and icon action
   419→
   420→For navigation, low-emphasis actions, and inline links.
   421→
   422→Rules:
   423→
   424→- Avoid multiple competing primary buttons in the same small region.
   425→- Use a consistent 8 px corner radius.
   426→- Include hover, active, focus, disabled, and loading states where relevant.
   427→- Loading must not cause unexpected layout shifts.
   428→- Disabled actions must be visually distinct and non-interactive.
   429→
   430→### 8.2 Inputs and property controls
   431→
   432→Inputs should resemble precision instruments rather than oversized form fields.
   433→
   434→- Compact labels positioned consistently above or beside the control.
   435→- Clear value alignment, especially for numeric properties.
   436→- Visible units when relevant, such as `180 px` or `35°`.
   437→- Validation feedback near the affected input.
   438→- Keyboard navigation and editing support.
   439→- A visible focus ring.
   440→- Consistent disabled and read-only styles.
   441→
   442→Numeric fields should support direct editing, while sliders provide rapid adjustment when a bounded range is appropriate.
   443→
   444→### 8.3 Cards and panels
   445→
   446→Use three structural patterns:
   447→
   448→- Flat regions: documentation sections and ordinary page content.
   449→- Bordered panels: property inspectors, code editors, and grouped controls.
   450→- Elevated overlays: dialogs, menus, command palettes, and popovers.
   451→
   452→Do not wrap every paragraph or documentation section in a card. Cards should represent actual grouping, navigation, or a distinct interactive area.
   453→
   454→### 8.4 Tabs and segmented controls
   455→
   456→Use tabs when switching between content views, such as JavaScript, HTML, and CSS examples.
   457→
   458→Use segmented controls when selecting one of a small set of related values, such as triangle, square, disk, or none.
   459→
   460→Requirements:
   461→
   462→- Clear selected state.
   463→- Keyboard support.
   464→- Consistent dimensions.
   465→- Accessible labels.
   466→- No reliance on color alone to communicate selection.
   467→
   468→### 8.5 Status badges
   469→
   470→Use small, low-emphasis labels for states such as Stable, Beta, Experimental, Deprecated, and Planned.
   471→
   472→The badge must communicate a real state. It should not be used merely as decoration or repeated for every shared property.
   473→

   510→### Workspace layout rules
   511→
   512→- The preview canvas should be visually distinct from the property inspector.
   513→- Keep toolbars compact and predictable.
   514→- Use the lemon accent for selected tools and important actions, not as a canvas background.
   515→- Property controls should be grouped logically and labeled consistently.
   516→- Code panels should use a dark editor-like surface in the dark theme and a readable equivalent in the light theme.
   517→- Allow the preview area to expand without forcing the inspector to expand with it.
   518→- On narrow screens, stack the inspector beneath the preview.
   519→
   520→### Preview isolation
   521→
   522→The component preview must be isolated from the platform's own styles where necessary. Use an explicit preview container and scoped styles so global documentation styles cannot unintentionally change the component's rendering.

   524→The website's visual theme must never become a mandatory dependency of the vanilla JavaScript library.

   526→## 10. Motion and interaction feedback
   527→
   528→Motion should communicate changes, not decorate every interaction.
   529→
   530→| Interaction         | Recommended behavior                                 |
   531→| ------------------- | ---------------------------------------------------- |
   532→| Button hover        | Subtle surface or brightness change                  |
   533→| Button press        | Brief pressed-state feedback                         |
   534→| Popover open        | Short opacity and small-scale transition             |
   535→| Sidebar collapse    | Smooth width transition where practical              |
   536→| Tab change          | Immediate content change or restrained transition    |
   537→| Property adjustment | Update preview immediately                           |
   538→| Copy action         | Brief confirmation label or icon state               |
   539→| Loading             | Subtle indicator that preserves layout               |
   540→| Color wheel drag    | Direct, immediate response without delayed animation |
   541→
   542→Suggested timing tokens:
   543→
   544→- `motion-fast`: 100–140 ms.
   545→- `motion-standard`: 160–220 ms.
   546→- `motion-emphasis`: 240–300 ms.
   547→
   548→Use easing that feels responsive and controlled. Do not animate numeric values or color changes in ways that make the component feel laggy during direct manipulation.
   549→
   550→Respect `prefers-reduced-motion`. Animation must not be the only way to communicate an important state change.

   552→## 11. Design tokens and CSS architecture
   553→
   554→The design system should use semantic CSS custom properties rather than scattering literal hex values throughout the website.
   555→
   556→Example token foundation:
   557→
   558→```
   559→:root {
   560→  color-scheme: light dark;
   561→

   609→### CSS architecture requirements
   610→
   611→- Separate global design tokens from component-specific tokens.
   612→- Use semantic roles such as `--surface`, `--text-primary`, and `--border` for everyday styling.
   613→- Keep brand-specific values separate from generic component behavior.
   614→- Avoid global selectors that unintentionally alter components embedded in other applications.
   615→- Document the supported customization API.
   616→- Use a clear prefix or another deliberate scoping strategy for library-owned CSS variables.
   617→- Do not make the library depend on the website's root theme tokens.
   618→
   619→A component may offer its own variables such as `--color-picker-ring-width` while retaining safe defaults when no custom values are provided.

   621→## 12. Accessibility and usability standards
   622→
   623→The design system must be accessible in both themes and across all supported interaction modes.
   624→
   625→### Requirements
   626→
   627→- Text and interactive controls meet WCAG 2.2 AA contrast requirements wherever applicable.
   628→- Keyboard focus is visible against dark and light surfaces.
   629→- Interactive controls have accessible names and appropriate semantic roles.
   630→- Icon-only controls include accessible labels and tooltips where useful.
   631→- Hover states have equivalent focus and touch behavior.
   632→- Error messages identify the affected input and explain how to correct it.
   633→- State changes are not communicated through color alone.
   634→- Components support keyboard interaction according to their control type.
   635→- Motion respects user preferences.
   636→- Touch controls have appropriately sized targets.
   637→
   638→For the lemon accent, dark text such as `#171521` should be used on the bright background. Do not assume white text will be readable on every purple or lemon shade; validate actual color combinations before release.

   722→## 15. Final design principles
   723→
   724→The final design system should follow these rules:
   725→
   726→1. Distinctive, not distracting. Black, purple, and lemon create identity without overpowering technical content.
   727→2. Functional over decorative. Every interactive preview and property control should do what it claims.
   728→3. Consistent but flexible. The website has one recognizable design language; components remain independently themeable.
   729→4. Precise, not cramped. Compact controls coexist with readable documentation and adequate spacing.
   730→5. Lightweight by design. Use reusable CSS tokens, carefully selected icon assets, and minimal runtime dependencies.
   731→6. Accessible by default. Contrast, keyboard operation, visible focus, and semantic controls are foundational.
   732→7. Honest documentation. Clearly distinguish available components, proposed features, static previews, and actual interactive implementations.
   733→
   734→The recommended starting combination is Obsidian `#101014` + Deep Violet `#211A30` + Lemon Signal `#D9FF66`, with Lucide for general icons and Simple Icons for external technology logos.
