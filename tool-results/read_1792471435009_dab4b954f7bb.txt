     1→# Page-by-Page UI Specification
     2→
     3→Vanilla JavaScript UI Components Platform · UX/UI Product Specification · v1.0
     4→
     5→This specification defines the actual interface of every website page: layout, content hierarchy, controls, interaction behavior, responsive states, and navigation. It builds on the platform structure established previously, without locking the website to a particular framework or implementation stack.
     6→
     7→The central design principle is that this is a working component workshop, not merely a component gallery. Developers should be able to discover a component, experiment with it, inspect its properties, and understand how to integrate it—all in one coherent experience.

    61→### 1.1 Header specification
    62→
    63→- Brand: logo and product name; click returns Home.
    64→- Primary navigation: Components, Documentation, Examples, Resources.
    65→- Search: global command-style search with keyboard shortcut.
    66→- Theme switch: light/dark mode, with system preference as an optional default.
    67→- Mobile menu: replaces or collapses primary navigation on narrow screens.
    68→- Repository link: external project link when available.
    69→
    70→The header remains consistent across routes. It should not grow into a large marketing navigation bar.
    71→
    72→### 1.2 Documentation sidebar
    73→
    74→The sidebar has two modes:
    75→
    76→- Library mode: categories and component names.
    77→- Documentation mode: guides, installation, concepts, theming, and API references.
    78→
    79→Behavior:
    80→
    81→- Expand and collapse category groups.
    82→- Highlight the active route.
    83→- Preserve the current scroll position when practical.
    84→- Support a compact mode on desktop and a drawer on mobile.
    85→- Do not display future components as if they already exist. Planned entries must be clearly marked or omitted.
    86→
    87→### 1.3 Content and utility regions
    88→
    89→The main content region supports text, interactive previews, code panels, and property inspectors. An optional right-hand table of contents appears on longer pages.
    90→
    91→On component detail pages, the preview and inspector are the primary work area. On documentation pages, readability takes priority over the three-column layout.

   208→### Required functionality
   209→
   210→Search
   211→
   212→- Search component names, descriptions, aliases, and supported properties.
   213→- Filter results as the query changes.
   214→- Show a useful empty state with a clear-search action.
   215→- Allow Escape to clear or close the search interface according to its state.
   216→
   217→Filters
   218→
   219→- Category.
   220→- Availability status, such as Stable, Beta, or Experimental.
   221→- Capabilities, such as Keyboard Support or Resizable, when metadata is available.
   222→
   223→Sorting
   224→
   225→Default ordering should be curated or alphabetical. Popularity sorting should only be introduced if the platform has a meaningful, transparent popularity measure.
   226→
   227→Component card behavior
   228→
   229→Each card includes a preview, name, concise description, category, and actual release status. Clicking it opens the component detail page.
   230→
   231→### URL and state behavior
   232→
   233→- Use query parameters for shareable search and filter states, for example `/components?category=color&q=wheel`.
   234→- Back and forward navigation must restore the relevant search state.
   235→- Opening a card should navigate to its canonical URL.
   236→
   237→### Empty and loading states
   238→
   239→- Loading: restrained skeleton cards.
   240→- No matches: explain that no components match the current filters.
   241→- Unavailable category: show a clear explanation rather than a broken page.
   242→- No network-dependent loading is required for core component previews when their assets and modules are bundled locally.

   368→### 5.2 Header and metadata
   369→
   370→Show:
   371→
   372→- Breadcrumb.
   373→- Component name and short summary.
   374→- Release status.
   375→- Category and relevant capability tags.
   376→- Link to source or repository, if available.
   377→- Link to report an issue or contribute.
   378→
   379→Do not place numerous low-value badges beside the title.
   380→
   381→### 5.3 Preview workspace
   382→
   383→The preview is the primary interactive region.
   384→
   385→Toolbar controls
   386→
   387→- Reset to defaults.
   388→- Optional preview-size selector.
   389→- Optional isolated-preview or expanded mode.
   390→- Optional background selector for components whose appearance depends on their surroundings.
   391→
   392→Only show controls that are useful for the current component.
   393→
   394→Preview behavior
   395→
   396→- Render the actual component.
   397→- Accept direct pointer and keyboard interaction.
   398→- Update the output panel and inspector when its state changes.
   399→- Respect the selected theme and preview dimensions.
   400→- Remain independent of the surrounding website's styling wherever possible.
   401→
   402→### 5.4 Property inspector
   403→
   404→For the Color Wheel Picker, the initial inspector should expose the following controls.
   405→
   406→| Property        | UI control                     | Behavior                                |
   407→| --------------- | ------------------------------ | --------------------------------------- |
   408→| Inner shape     | Four-option segmented selector | Changes triangle, square, disk, or none |
   409→| Inner size      | Numeric field and/or slider    | Changes inner shape dimensions          |
   410→| Initial hue     | Numeric field or slider        | Updates hue                             |
   411→| Initial color   | Color value input              | Sets the current selected color         |
   412→| Wheel thickness | Numeric field or slider        | Adjusts ring thickness if supported     |
   413→| Wheel spacing   | Numeric field or slider        | Adjusts inner gap if supported          |
   414→
   415→The property inspector should be generated from documented component capabilities or a defined property schema, rather than manually duplicating business logic for each preview.
   416→
   417→Control interaction rules
   418→
   419→- Apply valid changes immediately.
   420→- Validate numeric ranges and units.
   421→- Preserve unrelated property values when another property changes.
   422→- Keep the inspector synchronized with direct manipulation of the component.
   423→- Clearly distinguish default values from overridden values.
   424→- Provide a per-property reset where useful and a global reset for the entire preview.
   425→
   426→### 5.5 Output panel
   427→
   428→Display the selected color in a clear, copyable format.
   429→
   430→- Color swatch.
   431→- HEX value.
   432→- RGB values.
   433→- HSV values.
   434→- HSL values.
   435→
   436→Requirements:
   437→
   438→- Copy each representation independently.
   439→- Update values while the user interacts with the wheel.
   440→- Validate manually entered values.
   441→- Show a clear error for invalid input.
   442→- Keep the current selection synchronized regardless of whether the user changes it through the preview or the input fields.
   443→
   444→### 5.6 Code panel
   445→
   446→Tabs:
   447→
   448→- JavaScript: initialization and component configuration.
   449→- HTML: required container markup.
   450→- CSS: required styling or customization.
   451→- API: public methods, events, and properties.
   452→
   453→The code panel must:
   454→
   455→- Reflect the active configuration.
   456→- Use the actual public API.
   457→- Offer copy-to-clipboard.
   458→- Preserve readable formatting.
   459→- Explain dependencies and setup requirements.
   460→- Avoid showing framework-specific code as the primary integration path.
   461→
   462→A framework integration example may be offered as a separate optional guide, but the canonical example must work with plain HTML and JavaScript.
   463→
   464→### 5.7 Documentation below the playground
   465→
   466→Use a left-aligned documentation column with a contextual right-hand table of contents on wide screens.
   467→
   468→Sections:
   469→
   470→1. Overview.
   471→2. When to use it.
   472→3. Installation and basic usage.
   473→4. Interactive examples.
   474→5. Properties and defaults.
   475→6. Methods.
   476→7. Events.
   477→8. Styling and customization.
   478→9. Accessibility.
   479→10. Troubleshooting.
   480→
   481→Use anchor links and a clear active-section indicator.
   482→
   483→### 5.8 Playground states
   484→
   485→The component page must define:
   486→
   487→- Default configuration.
   488→- Modified configuration.
   489→- Invalid property input.
   490→- Reset state.
   491→- Preview rendering failure.
   492→- Copy success or failure.
   493→- Small viewport behavior.
   494→- Keyboard focus and interaction states.
   495→
   496→If a preview fails to load, preserve the documentation and display a useful error with a retry option where appropriate.

  1022→## 18. Global interaction and accessibility specification
  1023→
  1024→These requirements apply to all pages and all interactive previews.
  1025→
  1026→| Area                 | Required behavior                                                        |
  1027→| -------------------- | ------------------------------------------------------------------------ |
  1028→| Navigation           | Keyboard-accessible links, visible active state, correct browser history |
  1029→| Dialogs and overlays | Focus management, Escape handling, accessible labels                     |
  1030→| Inputs               | Labels, validation messages, keyboard support                            |
  1031→| Component previews   | Actual functional instances, not visual imitations                       |
  1032→| Code examples        | Readable formatting and reliable copy behavior                           |
  1033→| Loading              | Clear loading states without layout jumps                                |
  1034→| Errors               | Contextual messages and recovery where possible                          |
  1035→| Themes               | Consistent colors and contrast across the platform                       |
  1036→| Mobile               | Touch-friendly controls and no unintended horizontal overflow            |
  1037→| Motion               | Respect reduced-motion preferences                                       |
  1038→
  1039→### Component playground-specific requirements
  1040→
  1041→The playground must distinguish between three sources of state:
  1042→
  1043→1. Component state: The actual selected value and behavior inside the component.
  1044→2. Playground configuration: Properties set through the inspector.
  1045→3. Code representation: The configuration and initialization code shown to the developer.
  1046→
  1047→These must remain synchronized through a documented configuration model. The generated code must describe the actual component configuration, not an approximation of what the preview looks like.
