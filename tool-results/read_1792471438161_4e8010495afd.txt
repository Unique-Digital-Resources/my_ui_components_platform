     1→     1→# Page-by-Page UI Specification
     2→     2→
     3→     3→Vanilla JavaScript UI Components Platform · UX/UI Product Specification · v1.0
     4→     4→
     5→     5→This specification defines the actual interface of every website page: layout, content hierarchy, controls, interaction behavior, responsive states, and navigation. It builds on the platform structure established previously, without locking the website to a particular framework or implementation stack.
     6→     6→
     7→     7→The central design principle is that this is a working component workshop, not merely a component gallery. Developers should be able to discover a component, experiment with it, inspect its properties, and understand how to integrate it—all in one coherent experience.

    61→    61→### 1.1 Header specification
    62→    62→
    63→    63→- Brand: logo and product name; click returns Home.
    64→    64→- Primary navigation: Components, Documentation, Examples, Resources.
    65→    65→- Search: global command-style search with keyboard shortcut.
    66→    66→- Theme switch: light/dark mode, with system preference as an optional default.
    67→    67→- Mobile menu: replaces or collapses primary navigation on narrow screens.
    68→    68→- Repository link: external project link when available.
    69→    69→
    70→    70→The header remains consistent across routes. It should not grow into a large marketing navigation bar.
    71→    71→
    72→    72→### 1.2 Documentation sidebar
    73→    73→
    74→    74→The sidebar has two modes:
    75→    75→
    76→    76→- Library mode: categories and component names.
    77→    77→- Documentation mode: guides, installation, concepts, theming, and API references.
    78→    78→
    79→    79→Behavior:
    80→    80→
    81→    81→- Expand and collapse category groups.
    82→    82→- Highlight the active route.
    83→    83→- Preserve the current scroll position when practical.
    84→    84→- Support a compact mode on desktop and a drawer on mobile.
    85→    85→- Do not display future components as if they already exist. Planned entries must be clearly marked or omitted.
    86→    86→
    87→    87→### 1.3 Content and utility regions
    88→    88→
    89→    89→The main content region supports text, interactive previews, code panels, and property inspectors. An optional right-hand table of contents appears on longer pages.
    90→    90→
    91→    91→On component detail pages, the preview and inspector are the primary work area. On documentation pages, readability takes priority over the three-column layout.

   147→   147→### Interaction details
   148→   148→
   149→   149→- The featured component should be a real instance, not a screenshot.
   150→   150→- Hover states must be subtle and consistent with the library's visual language.
   151→   151→- Category cards are entirely clickable but must retain clear text links and keyboard accessibility.
   152→   152→- The hero should avoid exaggerated claims, counters, fake user testimonials, or unsupported compatibility badges.
   153→   153→
   154→   154→### Responsive behavior
   155→   155→
   156→   156→- Desktop: hero and featured component may appear side by side.
   157→   157→- Tablet: narrower two-column layout.

   208→   208→### Required functionality
   209→   209→
   210→   210→Search
   211→   211→
   212→   212→- Search component names, descriptions, aliases, and supported properties.
   213→   213→- Filter results as the query changes.
   214→   214→- Show a useful empty state with a clear-search action.
   215→   215→- Allow Escape to clear or close the search interface according to its state.
   216→   216→
   217→   217→Filters
   218→   218→
   219→   219→- Category.
   220→   220→- Availability status, such as Stable, Beta, or Experimental.
   221→   221→- Capabilities, such as Keyboard Support or Resizable, when metadata is available.
   222→   222→
   223→   223→Sorting
   224→   224→
   225→   225→Default ordering should be curated or alphabetical. Popularity sorting should only be introduced if the platform has a meaningful, transparent popularity measure.
   226→   226→
   227→   227→Component card behavior
   228→   228→
   229→   229→Each card includes a preview, name, concise description, category, and actual release status. Clicking it opens the component detail page.
   230→   230→
   231→   231→### URL and state behavior
   232→   232→
   233→   233→- Use query parameters for shareable search and filter states, for example `/components?category=color&q=wheel`.
   234→   234→- Back and forward navigation must restore the relevant search state.
   235→   235→- Opening a card should navigate to its canonical URL.
   236→   236→
   237→   237→### Empty and loading states
   238→   238→
   239→   239→- Loading: restrained skeleton cards.
   240→   240→- No matches: explain that no components match the current filters.
   241→   241→- Unavailable category: show a clear explanation rather than a broken page.
   242→   242→- No network-dependent loading is required for core component previews when their assets and modules are bundled locally.

   381→   381→### 5.3 Preview workspace
   382→   382→
   383→   383→The preview is the primary interactive region.
   384→   384→
   385→   385→Toolbar controls
   386→   386→
   387→   387→- Reset to defaults.
   388→   388→- Optional preview-size selector.
   389→   389→- Optional isolated-preview or expanded mode.
   390→   390→- Optional background selector for components whose appearance depends on their surroundings.
   391→   391→
   392→   392→Only show controls that are useful for the current component.
   393→   393→
   394→   394→Preview behavior
   395→   395→
   396→   396→- Render the actual component.
   397→   397→- Accept direct pointer and keyboard interaction.
   398→   398→- Update the output panel and inspector when its state changes.
   399→   399→- Respect the selected theme and preview dimensions.
   400→   400→- Remain independent of the surrounding website's styling wherever possible.

   402→   402→### 5.4 Property inspector
   403→   403→
   404→   404→For the Color Wheel Picker, the initial inspector should expose the following controls.
   405→   405→
   406→   406→| Property        | UI control                     | Behavior                                |
   407→   407→| --------------- | ------------------------------ | --------------------------------------- |
   408→   408→| Inner shape     | Four-option segmented selector | Changes triangle, square, disk, or none |
   409→   409→| Inner size      | Numeric field and/or slider    | Changes inner shape dimensions          |
   410→   410→| Initial hue     | Numeric field or slider        | Updates hue                             |
   411→   411→| Initial color   | Color value input              | Sets the current selected color         |
   412→   412→| Wheel thickness | Numeric field or slider        | Adjusts ring thickness if supported     |
   413→   413→| Wheel spacing   | Numeric field or slider        | Adjusts inner gap if supported          |
   414→   414→
   415→   415→The property inspector should be generated from documented component capabilities or a defined property schema, rather than manually duplicating business logic for each preview.
   416→   416→
   417→   417→Control interaction rules
   418→   418→
   419→   419→- Apply valid changes immediately.
   420→   420→- Validate numeric ranges and units.
   421→   421→- Preserve unrelated property values when another property changes.
   422→   422→- Keep the inspector synchronized with direct manipulation of the component.
   423→   423→- Clearly distinguish default values from overridden values.
   424→   424→- Provide a per-property reset where useful and a global reset for the entire preview.
   425→   425→

   434→   434→- HSL values.

   437→   437→

   440→   440→- Validate manually entered values.
   441→   441→- Show a clear error for invalid input.
   442→   442→- Keep the current selection synchronized regardless of whether the user changes it through the preview or the input fields.

   447→   447→
   448→   448→- JavaScript: initialization and component configuration.
   449→   449→- HTML: required container markup.
   450→   450→- CSS: required styling or customization.
   451→   451→- API: public methods, events, and properties.
   452→   452→
   453→   453→The code panel must:
   454→   454→
   455→   455→- Reflect the active configuration.
   456→   456→- Use the actual public API.
   457→   457→- Offer copy-to-clipboard.
   458→   458→- Preserve readable formatting.

   460→   460→- Avoid showing framework-specific code as the primary integration path.

  1023→  1023→
  1024→  1024→These requirements apply to all pages and all interactive previews.
  1025→  1025→
  1026→  1026→| Area                 | Required behavior                                                        |
  1027→  1027→| -------------------- | ------------------------------------------------------------------------ |
  1028→  1028→| Navigation           | Keyboard-accessible links, visible active state, correct browser history |
  1029→  1029→| Dialogs and overlays | Focus management, Escape handling, accessible labels                     |
  1030→  1030→| Inputs               | Labels, validation messages, keyboard support                            |
  1031→  1031→| Component previews   | Actual functional instances, not visual imitations                       |
  1032→  1032→| Code examples        | Readable formatting and reliable copy behavior                           |
  1033→  1033→| Loading              | Clear loading states without layout jumps                                |
  1034→  1034→| Errors               | Contextual messages and recovery where possible                          |
  1035→  1035→| Themes               | Consistent colors and contrast across the platform                       |
  1036→  1036→| Mobile               | Touch-friendly controls and no unintended horizontal overflow            |
  1037→  1037→| Motion               | Respect reduced-motion preferences                                       |
  1038→  1038→
  1039→  1039→### Component playground-specific requirements
  1040→  1040→
  1041→  1041→The playground must distinguish between three sources of state:
  1042→  1042→
  1043→  1043→1. Component state: The actual selected value and behavior inside the component.
  1044→  1044→2. Playground configuration: Properties set through the inspector.
  1045→  1045→3. Code representation: The configuration and initialization code shown to the developer.
  1046→  1046→
  1047→  1047→These must remain synchronized through a documented configuration model. The generated code must describe the actual component configuration, not an approximation of what the preview looks like.

  1069→  1069→### Responsive behavior rules
  1070→  1070→
  1071→  1071→- The right-hand table of contents disappears before the main content becomes cramped.
  1072→  1072→- The component inspector moves below the preview on narrow screens.
  1073→  1073→- Code blocks may scroll horizontally, but the page itself should not.
  1074→  1074→- Search results remain usable with touch and keyboard input.
  1075→  1075→- The color picker retains sufficient size and precision for touch interaction.
  1076→  1076→- No essential property or action should be available only on hover.
  1077→  1077→
  1078→  1078→Use content-driven breakpoints rather than assuming all devices fit a particular fixed width.
